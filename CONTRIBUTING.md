# Contributing Guide 🤝

Thank you for your interest in contributing to this Git learning repository! This guide will help you make your first (or next) contribution.

## Quick Start

1. **Fork** this repository
2. **Clone** your fork: `git clone https://github.com/YOUR-USERNAME/LBMC_tutorial_collaborative_git.git`
3. **Create a branch**: `git checkout -b my-contribution`
4. **Make changes** and commit: `git commit -m "Description of changes"`
5. **Push**: `git push origin my-contribution`
6. **Create a Pull Request** on GitHub

## Contribution Guidelines

### For All Contributions

1. **Check existing PRs and issues** - Someone might already be working on it
2. **One PR per topic** - Keep changes focused and reviewable
3. **Test your changes** - Make sure markdown renders correctly
4. **Follow existing style** - Match the formatting of existing files

### For Content

1. **Be beginner-friendly** - Remember your audience
2. **Provide examples** - Show, don't just tell
3. **Use clear language** - Avoid jargon or explain it
4. **Credit sources** - Link to resources you reference

### For Code/Scripts

1. **Comment your code** - Help others understand
2. **Keep it simple** - This is a learning repository
3. **Include instructions** - How to run your script

## Commit Message Guidelines

Good commit messages help everyone understand the project history.

### Format

```
Type: Brief description (50 chars or less)

More detailed explanation if needed (wrap at 72 chars).
Explain what and why, not how.
```

### Types

- **Add**: New content or features
- **Fix**: Bug fixes or corrections
- **Update**: Changes to existing content
- **Remove**: Removing content
- **Docs**: Documentation changes
- **Style**: Formatting, no content change

### Examples

✅ **Good commit messages:**
```
Add: Include myself in contributors list
Fix: Correct git clone command in README
Update: Improve merge conflict explanation
Docs: Add guide for Git hooks
```

❌ **Bad commit messages:**
```
update
fixes
asdf
changes
```

## Pull Request Guidelines

### Creating a PR

1. **Use a descriptive title**
   ```
   Add beginner's guide to Git branches
   Fix typo in GETTING_STARTED.md
   Update resources with interactive tutorials
   ```

2. **Provide context in description**
   ```markdown
   ## What
   Added a new section explaining Git branches
   
   ## Why
   Many beginners struggle with understanding branches
   
   ## How
   Created a step-by-step guide with examples and visuals
   ```

3. **Reference related issues**
   ```markdown
   Closes #123
   Related to #456
   ```

### PR Checklist

Before submitting, verify:

- [ ] My changes are focused on a single topic
- [ ] I've tested my changes (links work, markdown renders)
- [ ] My commit messages are clear and descriptive
- [ ] I've updated relevant documentation
- [ ] My changes follow the existing style
- [ ] I've checked for typos and errors

## Review Process

### What to Expect

1. **Automated checks** - Basic validation (if any)
2. **Maintainer review** - A maintainer will review your PR
3. **Feedback** - You might receive suggestions for improvements
4. **Iteration** - Make requested changes
5. **Approval and merge** - Once approved, your PR will be merged!

### Responding to Feedback

- Be open to suggestions - reviewers want to help!
- Ask questions if feedback isn't clear
- Make requested changes or discuss alternatives
- Thank reviewers for their time
- Don't take it personally - it's about the code/content, not you
